# Summons: what a Gloomhaven summon needs in Frosthaven (research, 2026-10-27)

The class roadmap puts every class with summons after a "summon-model step" (G3 builds it on the two Jaws of the
Lion summons, G4-G6 depend on it). This note is what that step is, from both games' data and Frosthaven's decompiled
code, so G3 can start from a plan rather than a question.

## Findings

**1. The data port is trivial.** Both games define a hero summon the same way (`Parser: HeroSummon`, `ID`, `LocKey`,
`Model`, `Health/Move/Attack/Range` with enhancement slots, `OnSummonAbilities`). Gloomhaven has 41
(`HeroSummon/*.yml` in its rule archives), Frosthaven 41 of its own. The only conversion is the one the cards already
get: `Enhancements:` -> `SquareEnhancements:` (gh_port.convert_enhancements), card text keys, and the summon's name
string. `gh_port.py` does not copy them yet: a class's summon cards (`Summon: BattleBoarID`) name defs the pack
doesn't carry.

**2. Frosthaven's rules still know every Gloomhaven summon model.** `HeroSummonYML` parses `Model:` through
`CClass.ENPCModel`, and that enum (407 members) contains all 41 Gloomhaven summon models (BattleBoar,
BeastTyrantBear, RedFalcon, Skeleton...). No parser work.

**3. The model is the whole job.** Frosthaven loads an NPC's prefab from a bundle named `npc_<model>` (lower-case,
`AssetBundleManager.BundleConfigForPrefab`), listed in its `BundleLoadConfigs`; a model with no bundle falls to
`npc_none`/NULLCharacter and `CreateCharacterActor` throws "Unable to find character with prefab name" — the
scenario's error screen. Frosthaven's `AssetBundles/Base` has no Gloomhaven summon bundle.

**4. Gloomhaven ships one self-contained bundle per summon, in Frosthaven's own layout.** 171 `npc_*_assets_all.bundle`
files under `GH_Data/StreamingAssets/aa/StandaloneWindows64`, 8-20 MB each (`npc_battleboar` 8 MB,
`npc_beasttyrantbear` 20 MB), each with `Assets/_AssetBundles/npcs/<Model>.prefab` — the same container path and the
same component set as a Frosthaven NPC bundle (`CharacterManager`, `Outlinable`, `MaterialLoader`, `SummonAppear`,
`DeathDissolve`, `FootstepSound`, SMB scripts, its own Animator and clips). The DLC summons (Sand Devil, Ward) are
`dlc_dlc1_npc_*` with the DLC prefab path.

**5. Why it still can't be dropped in as is.** The hero port learned this already (GHModel.cs): a Gloomhaven prefab's
MonoBehaviours reference Gloomhaven's scripts, its materials use Gloomhaven's shaders, and its SMB/choreographer
hooks are tuned to that game. GHModel therefore builds a *template* per class: the Drifter's prefab is cloned and
the Gloomhaven mesh, materials (rebuilt on Frosthaven's shaders, gh_model._materials) and animation clips (grafted
onto the Drifter's controller, gh_model._animation) are swapped in; `GetCharacterPrefabFromBundle` hands that
template back. A summon needs the same, with an NPC template.

## The plan for G3

1. **gh_port: carry the summons.** For each ported class, copy the HeroSummon defs its cards name (convert
   enhancements, text keys), add their name strings, and list them in pack.json; `packcheck` fails on a `Summon:`
   that names a def the pack lacks. (Small.)
2. **gh_model: export an NPC.** `export()` today takes a hero bundle and the Drifter's; add an NPC path that takes
   `npc_<model>_assets_all.bundle` and a Frosthaven NPC bundle as the template (a Frosthaven summon of similar
   build: a four-legged one for the boar/bear/wolves, a flyer for the falcons/hawk, a biped for the skeleton...),
   and exports mesh + materials-on-FH-shaders + clips the way the hero path does. The animator mapping is the
   unknown: NPC controllers are simpler than a hero's (idle / move / attack / hit / death), so the clip-slot match
   should be easier than the Drifter's 25 states, but it is per template. (The main work.)
3. **GHModel: NPC templates.** A second template family keyed by `ENPCModel`: clone the chosen Frosthaven NPC
   prefab, graft the exported pieces, and return it from `GetCharacterPrefabFromBundle` (prefix on the NPC branch of
   `BundleConfigForPrefab`/`GetCharacterPrefabFromBundle`, same place the hero hook sits). Register nothing in
   `BundleLoadConfigs`: the hook answers before the lookup.
4. **Test on the bench**: Red Guard's Sand Devil and Voidwarden's Ward (DLC bundles, the simplest cases) first, then
   the Beast Tyrant's bear (it is a *companion*: created at scenario start, `Filter: Companion`,
   `ForgoActionsForCompanion`, `Swap` — the system probe for the bear waits for this step).
5. **Fallback** worth keeping: if a model's export fails, the summon still *works* with any Frosthaven NPC model of
   the right size (step 3 can return the template unmodified), so a class never blocks on art.

## Status (2026-10-27, later)

Built, not yet seen in game:
- Data: `gh_model.export_npc` (bundle lookup `npc_<model>_assets_all*` / `dlc_*_npc_<model>*`, the clip table by Frosthaven
  state name against the Polar Cat's controller, wrapper/model prefabs, CharacterManager TargetBone/Height/HitRadius,
  materials), wired into `gh_port.py` as pack.json `summon_models`. Checked end to end on a scratch port of the Mindthief:
  GiantRat, PlagueRat, RatKing exported (11 MB each, 2 materials, heights 0.58/0.58/0.69, base PolarCat).
- Plugin: `GHModel.SummonTemplate(model)` builds the summon on the Polar Cat's prefab (visual swapped, materials on
  Frosthaven's shaders, VFXLookup/AnimFXTrigger/DeathDissolve/Outlinable/IdleAnimParams/FootstepSound, override
  controller with the Gloomhaven clips, carrier with the template's CharacterManager values); `GHClasses` hooks
  `GetCharacterPrefabFromBundle` (NPC branch), `EnsureActorPrefabBundlesLoadedBeforeAction` and
  `GetBundlesNeededForRequirements` (`npcModelsNeeded`) so the template's bundle is what gets loaded. A failed build
  falls back to the Polar Cat itself. hookcheck 269/269.
- Next: bench a summon (Mindthief's Rat Swarm / Red Guard's Sand Devil as probe ports) once the Group 2 pass frees
  the game; judge the animator mapping on the shots (Idle-Run, Attack, Hit, Death).
